# Resources are self-sufficient types that name their parent

A resource is a type whose fields are what its own part of a URL carries (the parameters of its part of the path, its fields of the query string). Each resource names the resource it is nested in; the shape of the path says nothing about nesting, and `/catalogs` and `/catalogs/{catalog_id}` are two separate resources, neither inside the other, only because the app declared them so.

A resource holds nothing of the resources around it. Where it stands is a resource path, `ResourcePath<R>`: the resource's value and, above it, the path of its parent, up to the root resource. The library parses a URL into a resource path and a resource path prints itself back as that URL. A controller and a presenter receive the path of their resource, from which they read its fields, reach the values of the resources around it (`at.parent()`) and make the paths of the resources beside it (`at.parent().to(..)`) and nested in it (`at.to(..)`). A resource path is the only way to a URL: a link made from one cannot point at a route that does not exist, and no address is put together as a string.

What a resource shows is a view, chosen by its presenter ([ADR 6](0006-a-resource-answers-through-a-controller-and-a-presenter.md)). A view is not a resource and has no path of its own.

## Considered Options

- **Nesting read from the path** (the first part is one resource, each further part a resource nested in it): forces a detail resource inside the list's frame, which is the app's choice to make.
- **A tree declared top-down in one place**: the parent knows its children for free, but a resource's URL would depend on where it was mounted and links could only be checked at run time.
- **Handler functions** as in plain axum: no typed links, and the state of the URL is not a value the app can hold.
- **A nested resource repeats its ancestors' parameters as fields of its own** (`Item { id, item }` under `Catalog { id }`), and prints its URL alone (`.url() -> String`): what was first built. No new type, but the same value is written at every depth, a resource can be built with an `id` its parent would not have, an ancestor's field of the query string is lost in a nested resource's link unless it is repeated too (when the ancestor needs it, the link answers `400`), and a URL is a `String` like any other.
- **A nested resource holds its parent as a field** (`struct Item { catalog: Catalog, item_id }`): the parent's state inside the child again, and a field that is a struct, which serde cannot flatten into typed fields.
- **Parents load data and hand it down**, or **parents draw the navigation of their children**: both make a resource's answer depend on its parent having been asked, which it has not when only the nested view is sent ([ADR 1](0001-server-cuts-the-response-by-outlet.md)).

## Consequences

- A resource's fields are read and printed with serde, as one list of names and values: a path parameter fills the field it names (`{id}` fills `id`) and the query string fills the others. So each field holds a plain value, or a list of them that the query string carries by repeating the name (`?tag=tea&tag=green`), and a resource declares no parser and no printer of its own.
- Every resource on the way down is parsed from the same fields of the URL, and printing puts them back: each resource's fields fill the parameters of its own part of the path, and every resource's other fields make the one query string. So a nested resource's URL carries its ancestors' query string, and a field's name is used once on the way down (`catalog_id`, then `item_id`).
- A path starts from a resource whose ancestors carry nothing, each being its `Default` (`Catalog { catalog_id }.path()`, the root resource unnamed), and goes down one resource at a time (`.to(Item { item_id })`). A resource whose parent needs a value does not start a path, and `to` takes only a resource that names the path's resource as its parent: both are refused by the compiler.
- A path is shared, not copied (an `Arc`), so going down from one borrows it and no resource needs `Clone`. The only bound the design adds is `Default`, on the ancestors left out when a path starts.
- One resource, one address, and a GET on it always answers with the same resource. What it is shown as is a representation, chosen from the request: for a browser, a view. What one domain object looks like in two places (an appointment for its doctor and for its patient) is two resources, each with a view for its own reader; the views may share components. A resource nested in another adds a part to the path, and one that adds none is refused when it is registered. Two resources at one address would be two things with one identifier. Only the root resource has the empty part: its address is `/`, and its view is the document around every other view. What needs no address is not a resource: markup shared by views is a function, and what keeps state without changing the path is a region.
- A URL that does not parse into the resource's fields, or into those of an ancestor, is a client error (`400`), answered before any controller runs.
- The compiler checks a link's fields where the link is made. That a path's parameter has a field of the same name is not checked by the compiler, which cannot compare a path's text with a type's fields without a macro. It is checked when the resource is registered, each resource on the way against its own part of the path, together with a field named as one of an ancestor's: the app does not start.
- The parts of a path are joined as written, except that a part's last `/` gives way to a next part that starts with one (`/` then `/activity` is `/activity`, `/` then `recent` is `/recent`), and a whole path that is empty is `/`.
- An outlet's id is made of the names of the resources from the root resource down to its own, as their types spell them: a `-` joins the resources and a `_` joins the words of one resource's name (`document-outlet`, `document-catalog-outlet`, `document-catalog_item-outlet`). A resource does not choose it. Composed like the path, it is not shared by two outlets of one document. Two resources with the same type name and the same parent, which Rust allows in two modules, are given the same id; they are never in one document together. It is known without rendering, which the server needs to tell which outlet a request names ([ADR 1](0001-server-cuts-the-response-by-outlet.md)).
- The library does not say who draws the tabs. Each tab's view draws them, from the resource paths its presenter gave it, with itself marked as the open one, so the answer to a tab's address holds the tabs and the content together, as htmx's own tabs example does. The view around the tabs does not say which one is open.
- On a narrow swap the resources around are not asked, but their values are still read from the URL: a resource path is whole. A check that must hold for everything nested in a resource (may this reader see it) belongs to the use cases, not to the resource around.
- The controllers of a resource and of one nested in it may each read the same thing on a full load.
