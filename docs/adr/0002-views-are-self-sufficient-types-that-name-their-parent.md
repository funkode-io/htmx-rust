# Views are self-sufficient types that name their parent

A view is a type whose fields are what its own part of a URL carries (the parameters of its part of the path, its fields of the query string). Each view names the view it is nested in; the shape of the path says nothing about nesting, and `/catalogs` and `/catalogs/{catalog_id}` are two separate views, neither inside the other, only because the app declared them so. A view loads its own data and draws everything that is its own, including where it stands among its siblings.

A view holds nothing of the views around it. Where it is shown is a path, `ViewPath<V>`: the view's value and, above it, the path of its parent, up to the root view. The library parses a URL into a path, a path prints itself back as that URL, and a view renders at its path (`render(at: &ViewPath<Self>, ..)`), from which it reads its own fields, reaches its ancestors' values (`at.parent()`) and makes the paths of the views beside it (`at.parent().to(..)`) and nested in it (`at.to(..)`). A path is the only way to a URL: a link made from one cannot point at a route that does not exist, and no address is put together as a string.

## Considered Options

- **Nesting read from the path** (the first part is one view, each further part a view nested in it): forces a detail view inside the list's frame, which is the app's choice to make.
- **A tree declared top-down in one place**: the parent knows its children for free, but a view's URL would depend on where it was mounted and links could only be checked at run time.
- **Handler functions** as in plain axum: no typed links, and the state of the URL is not a value the app can hold.
- **A nested view repeats its ancestors' parameters as fields of its own** (`Item { id, item }` under `Catalog { id }`), and prints its URL alone (`view.url() -> String`): what was first built. No new type, but the same value is written at every depth, a view can be built with an `id` its parent would not have, an ancestor's field of the query string is lost in a nested view's link unless it is repeated too (when the ancestor needs it, the link answers `400`), and a URL is a `String` like any other.
- **A nested view holds its parent's view as a field** (`struct Item { catalog: Catalog, item_id }`): the parent's state inside the child again, and a field that is a struct, which serde cannot flatten into typed fields.
- **Parents load data and hand it down**, or **parents draw the navigation of their children**: both make a view depend on its parent having run, which it has not when only the nested view is sent ([ADR 1](0001-server-cuts-the-response-by-outlet.md)).

## Consequences

- A view's fields are read and printed with serde, as one list of names and values: a path parameter fills the field it names (`{id}` fills `id`) and the query string fills the others. So each field holds a plain value, or a list of them that the query string carries by repeating the name (`?tag=tea&tag=green`), and a view declares no parser and no printer of its own.
- Every view on the way down is parsed from the same fields of the URL, and printing puts them back: each view's fields fill the parameters of its own part of the path, and every view's other fields make the one query string. So a nested view's URL carries its ancestors' query string, and a field's name is used once on the way down (`catalog_id`, then `item_id`).
- A path starts from a view whose ancestors carry nothing, each being its `Default` (`Catalog { catalog_id }.path()`, the root view unnamed), and goes down one view at a time (`.to(Item { item_id })`). A view whose parent needs a value does not start a path, and `to` takes only a view that names the path's view as its parent: both are refused by the compiler.
- A path is shared, not copied (an `Arc`), so going down from one borrows it and no view needs `Clone`. The only bound the design adds is `Default`, on the ancestors left out when a path starts.
- One view, one address. What one domain object looks like in two places (an appointment for its doctor and for its patient) is two views, each a representation for its own reader, which share components and not a type. A view is a resource, so its address is its own: a view nested in another adds a part to the path, and one that adds none is refused when it is registered. Two views at one address would be two resources with one identifier, and nothing in the URL would say which is shown. Only the root view has no part: it is the document around every other view. What needs no address is not a view: markup shared by views is a function, and what keeps state without changing the path is a region.
- A URL that does not parse into the view's fields, or into those of an ancestor, is a client error (`400`), answered before any view runs.
- The compiler checks a link's fields where the link is made. That a path's parameter has a field of the same name is not checked by the compiler, which cannot compare a path's text with a type's fields without a macro. It is checked when the view is registered, each view on the way against its own part of the path, together with a field named as one of an ancestor's: the app does not start.
- The parts of a path are joined as written, except that a part's last `/` gives way to a next part that starts with one (`/` then `/activity` is `/activity`, `/` then `recent` is `/recent`), and a whole path that is empty is `/`.
- An outlet's id is made of the names of the views from the root view down to its own, as their types spell them: a `-` joins the views and a `_` joins the words of one view's name (`document-outlet`, `document-catalog-outlet`, `document-catalog_item-outlet`). A view does not choose it. Composed like the path, it is not shared by two outlets of one document. Two views with the same type name and the same parent, which Rust allows in two modules, are given the same id; they are never in one document together. It is known without rendering, which the server needs to tell which outlet a request names ([ADR 1](0001-server-cuts-the-response-by-outlet.md)).
- The library does not say who draws the tabs. Each tab draws them from its parent's path, with itself marked as the open one, so the answer to a tab's address holds the tabs and the content together, as htmx's own tabs example does. The view around the tabs does not say which one is open. From the registered views the library will also tell each view its siblings and its children (title, path, which one is shown), in the order of registration.
- On a narrow swap the ancestors do not render, but their values are still read from the URL: the path a view is shown at is whole. A check that must hold for every view nested in a resource's view (may this reader see it) belongs to the domain or to an axum layer, not to the parent view.
- A parent and its child may each load the same thing on a full load.
